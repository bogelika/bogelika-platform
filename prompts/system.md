# BOGELIKA Platform — общие инструкции

Ты работаешь над системой автоматизации сети студий красоты «БОГЕЛИКА»

Основной текущий модуль — Telegram-бот для приёма, проверки и хранения отчётов мастеров

## Перед началом любой задачи

Обязательно изучи:

- README.md
- AGENT.md
- TODO.md, если он существует
- всю документацию в папке docs/
- соответствующие JSON-файлы в папке workflows/
- связанные файлы в папках code/, prompts/ и examples/

Если документация противоречит реальному workflow, считай экспортированный workflow источником текущего фактического состояния и обязательно сообщи о противоречии

## Приоритеты проекта

1. Сохранность данных
2. Надёжность
3. Простота поддержки
4. Минимальные изменения существующей логики
5. Защита от дублей
6. Возможность повторной обработки после временных сбоев
7. Масштабирование на Telegram, MAX и ВКонтакте без дублирования логики

## Основные технические принципы

- отчёт сначала сохраняется в технической базе, только потом экспортируется во внешние сервисы
- Google Sheets является рабочей витриной, а не единственным хранилищем
- каждый отчёт связывается через уникальный report_key
- дополнение должно обновлять существующий отчёт, а не создавать новый
- временный сбой Google, Telegram, Timeweb или n8n не должен приводить к потере данных
- большие изменения нельзя вносить без предварительного плана
- не удаляй существующую рабочую логику без доказанной необходимости
- не проводи рефакторинг одновременно с исправлением отдельной ошибки
- не сохраняй в репозитории токены, API-ключи, Client Secret, пароли и credentials

## Работа с командами

Для анализа разрешены безопасные команды чтения:

- git status
- git diff
- git log
- git ls-files
- rg
- dir
- ls
- cat
- Get-Content

Без явного разрешения запрещены:

- git add
- git commit
- git push
- git pull
- git reset
- git checkout
- git restore
- rm
- del
- Remove-Item
- перемещение или удаление файлов
- изменение внешних сервисов
- публикация workflow в n8n
- изменение Google Sheets, Google Drive, Telegram или Timeweb

## Перед изменениями

Сначала напиши:

1. Что обнаружено
2. Что предлагается изменить
3. Почему выбран именно этот вариант
4. Какие файлы будут изменены
5. Какие есть риски
6. Как проверить результат

Начинай изменять файлы только после явного разрешения пользователя

## После реализации

В зависимости от изменений обнови:

- docs/CHANGELOG.md — после любого значимого изменения
- docs/FEATURES.md — если добавлена или изменена функция
- docs/WORKFLOWS.md — если изменён workflow
- docs/DATABASE.md — если изменена структура данных
- docs/ARCHITECTURE.md — если изменилась архитектура
- docs/ROADMAP.md — если изменился план развития
- docs/DECISIONS.md — если принято важное техническое решение

Не создавай коммиты и не отправляй изменения в GitHub без отдельного разрешения
