# DECISIONS

В этом документе фиксируются ключевые технические решения проекта и причины их принятия.

---

# 2026-07-15

## Использование Data Tables как основной базы

Решение

Основной технической базой проекта являются Data Tables n8n.

Причина

Google Sheets не гарантирует сохранность данных при временных сбоях.

---

## Google Sheets используется только как рабочая витрина

Решение

Google Sheets не считается основной базой.

Причина

Управляющим удобно работать с таблицей, но техническое хранение должно происходить отдельно.

---

## report_key является главным идентификатором

Решение

Каждый отчёт получает уникальный report_key.

Используется для связи:

- фотографий
- частей альбома
- отчёта
- строки Google Sheets
- будущей папки Google Drive
- записи WorkClient

Причина

Позволяет избежать дублей и безопасно обновлять существующий отчёт.

---

## Сначала сохранение — потом экспорт

Решение

Любой отчёт сначала сохраняется в технической базе.

Только после этого начинается экспорт во внешние сервисы.

Причина

При временном сбое Google, Telegram или Timeweb данные не теряются.

---

## AI используется как помощник

Решение

ИИ не принимает окончательное решение.

Он только:

- анализирует текст
- анализирует фотографии
- формирует рекомендации

Причина

Ответственность остаётся за управляющим.

---

## Один общий механизм отчётов

Решение

Telegram, MAX и ВКонтакте будут использовать одну и ту же логику обработки отчётов.

Причина

Чтобы не поддерживать несколько разных систем.

---

## Документация хранится в GitHub

Решение

Все изменения проекта сопровождаются обновлением документации.

Причина

Любой разработчик или AI должен понимать проект без дополнительных объяснений.


## Единая логика для Telegram, MAX и ВКонтакте

### Решение

Telegram, MAX и ВКонтакте будут использовать общую бизнес-логику, общую базу данных и общую базу знаний

Для каждого канала создаётся отдельный адаптер, который преобразует входящие сообщения в единый внутренний формат

### Причина

Отдельная реализация логики для каждого мессенджера приведёт к:

- дублированию workflow
- разным правилам проверки
- сложному сопровождению
- расхождению данных
- необходимости исправлять одну ошибку в нескольких местах

### Следствие

Общие проверки, AI-анализ, работа с отчётами и интеграции должны быть независимы от конкретного мессенджера

# 2026-10-07

## Один Telegram-бот для отчётов и поиска

### Решение

Отчёты, поиск отчётов мастером и вход в личный кабинет идут через **один** Bot Token и один основной workflow.

Отдельный бот поиска переводится в режим редиректа и затем отключается.

### Причина

- Мастерам проще один чат и одно меню.
- Одна проверка доступа и один реестр `staff_directory_pilot`.
- Меньше дублирования workflow и расхождений в логике.

### Следствие

Поиск и кабинет — отдельные subflow / webhook API, но не отдельная бизнес-логика отчётов.

---

## Реестр сотрудников в Data Tables

### Решение

Список людей с доступом к боту хранится в `staff_directory_pilot`, а не в Google Sheets и не «в голове у admin».

Offboarding = `status: disabled`, история отчётов не удаляется.

### Причина

Sheets — витрина; при сбое нельзя потерять контроль доступа. Нужна наглядность, кто подключён к Telegram.

### Следствие

Перед обработкой сообщения n8n проверяет активную карточку по `telegram_user_id`.

---

## Личный кабинет: сначала Mini App, затем сайт

### Решение

Первая версия кабинета — Telegram Mini App в том же боте. Веб-кабинет на поддомене — второй этап с тем же Cabinet API.

### Причина

Быстрее доставить ценность мастерам; управляющим для offboarding достаточно телефона на старте.

### Следствие

Backend один (n8n webhook + проверка WebApp initData).
