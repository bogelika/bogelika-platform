# Единый бот, поиск отчётов и личный кабинет

Документ описывает большое обновление платформы BOGELIKA: объединение ботов, доступ мастеров к поиску своих отчётов и личный кабинет для управления доступами.

Статус: **проектирование → поэтапная реализация**

---

## Зачем

1. **Один вход для мастера** — не переключаться между «ботом отчётов» и «ботом поиска».
2. **Поиск для каждого мастера** — быстро найти свой отчёт (клиент, дата, статус), не лезть в общую таблицу.
3. **Наглядность по людям** — видно, кто подключён к боту, какая роль и студия, кого давно не было в активности; при уходе сотрудника доступ отключается явно, а не «забыли в списке».

---

## Целевой опыт пользователя

### Мастер (Telegram)

Главное меню бота:

| Кнопка | Действие |
|--------|----------|
| ➕ Новый отчёт | Текущий сценарий PILOT без изменений логики сессии |
| 🔍 Мои отчёты | Поиск и просмотр **только своих** отчётов |
| 👤 Кабинет | Telegram Mini App: профиль, студия, последние отчёты, ссылка на инструкцию |
| ℹ️ Как отправить отчёт | Текущая инструкция |

Поиск внутри «Мои отчёты» (минимальный набор v1):

- последние 10 отчётов списком;
- поиск по фамилии клиента (частичное совпадение);
- фильтр по периоду (7 / 30 дней);
- карточка отчёта: дата, клиент, статус, фрагмент текста, количество фото (ссылки на Drive — когда появятся).

### Управляющий / администратор сети

- **Telegram Mini App «Кабинет»** (расширенная вкладка при роли `manager` / `admin`):
  - список сотрудников по студиям;
  - статус: активен / отключён / не привязан Telegram;
  - привязка `telegram_user_id` к карточке мастера;
  - отключение доступа одной кнопкой (без удаления истории отчётов).
- **Веб-кабинет** (этап 2, см. ниже) — удобнее для массовых правок и аудита.

### Собственник

- Те же инструменты, что у admin, плюс сводка по сети (позже — BI / Agent 6).

## Архитектурное решение: один бот

```text
Telegram (один Bot Token)
        │
        ▼
n8n: TG — БОГЕЛИКА мастера — PILOT (единый workflow)
        │
        ├── Адаптер: разбор update → route + user context
        ├── Проверка доступа (staff_directory)
        │
        ├── route: report_*  → существующие subflow / ноды отчёта
        ├── route: search_*  → subflow поиска (tg_reports_pilot)
        └── route: cabinet_* → WebApp init data / webhook API
        │
        ▼
Data Tables (+ позже Google Sheets / Drive только как витрина)
```

**Отдельный бот поиска** после миграции:

- переводится в режим «только редирект» (сообщение + ссылка на основной бот) на 4–8 недель;
- затем отключается.

Это снижает риск, что часть мастеров останется на старом боте без поиска.

## Роли и правила доступа

| Роль | Отчёты: сдача | Поиск |
|------|----------------|-------|
| `master` | да | только где `master_staff_id` = его карточка **или** (fallback PILOT) совпадение ФИО из отчёта с каноническим ФИО в карточке |
| `manager` | да (если мастер) | отчёты своей студии |
| `admin` | да | все студии |
| `disabled` | нет | нет |

Проверка доступа выполняется **до** любой бизнес-логики (после `/start` и при каждом сообщении, кроме служебных callback для неавторизованных — там только текст «обратитесь к управляющему»).

Идентификатор пользователя в Telegram: `telegram_user_id` (строка).

## Новые Data Tables

### `staff_directory_pilot`

Канонический реестр людей, имеющих доступ к боту.

| Поле | Тип | Описание |
|------|-----|----------|
| id | string | UUID или авто id |
| studio | string | Нормализованное название студии |
| full_name | string | «Имя Фамилия» как в отчётах |
| role | string | `master` \| `manager` \| `admin` |
| status | string | `active` \| `disabled` |
| telegram_user_id | string | Пусто, пока человек не написал боту / не привязан |
| telegram_username | string | Опционально, для поддержки |
| hired_at | datetime | Опционально |
| left_at | datetime | Заполняется при offboarding |
| notes | string | Комментарий управляющего |
| created_at | datetime | |
| updated_at | datetime | |

Индекс по `telegram_user_id` (уникальный среди `active`).

### `staff_access_events_pilot` (опционально v1, желательно v1.1)

Аудит: кто включил/выключил доступ, привязал Telegram.

## Связь отчётов с реестром

В `tg_reports_pilot` добавить поля (миграция без перезаписи старых строк):

| Поле | Описание |
|------|----------|
| master_staff_id | id из `staff_directory_pilot` |
| submitted_by_user_id | telegram user id отправителя |

При сборке отчёта:

1. Определить отправителя по `user_id`.
2. Найти активную карточку в `staff_directory_pilot`.
3. Сверить ФИО мастера из текста с `full_name` (мягкое предупреждение при расхождении, не блокировать PILOT).
4. Записать `master_staff_id` и `submitted_by_user_id`.

Поиск для мастера v1: фильтр `submitted_by_user_id = текущий` **OR** `master_staff_id = текущая карточка`.

## Личный кабинет: Mini App vs сайт

| Критерий | Telegram Mini App | Отдельный сайт |
|----------|-------------------|----------------|
| Время до первой версии | Быстрее, мастера уже в Telegram | Дольше (auth, хостинг) |
| Управление списком сотрудников | Удобно на телефоне | Удобнее на десктопе |
| Уведомления | Уже в Telegram | Нужны отдельно |
| Offboarding | Достаточно для v1 | Лучше для HR/бухгалтерии позже |

**Рекомендация BOGELIKA:**

1. **Этап A** — Mini App «Кабинет» в том же боте (мастер: профиль + последние отчёты; admin: реестр staff).
2. **Этап B** — веб-кабинет на поддомене с входом через Telegram Login Widget **или** одноразовой ссылкой из бота (тот же backend API n8n).

Backend для Mini App и сайта — **один**: n8n webhook `GET/POST /cabinet/*` с проверкой `initData` Telegram WebApp.

## Изменения в workflow (n8n)

### 1. Переименование (косметика)

`TG — Приём отчётов мастеров — PILOT` → `TG — БОГЕЛИКА мастера — PILOT` (единая точка входа).

### 2. Новые маршруты в `Determine incoming action`

Добавить:

- `search_menu` — кнопка «🔍 Мои отчёты»
- `search_query` — текст в режиме поиска (сессия `mode: search`)
- `cabinet_open` — кнопка «👤 Кабинет» → URL WebApp
- callback `search_pick:<report_key>` — открыть карточку

Сессии: расширить `tg_report_sessions_pilot` полем `mode` (`report` | `search` | `idle`) **или** отдельная таблица `tg_user_sessions_pilot` — предпочтительно одна таблица с полем `mode`, чтобы не плодить сущности.

### 3. Subflow «Проверка доступа»

- Lookup `staff_directory_pilot` by `telegram_user_id` + `status=active`.
- Если не найден — попытка «ожидает привязки» только для admin (ручная привязка), иначе стоп.

### 4. Subflow «Поиск отчётов»

- Вход: user context + query params.
- Чтение `tg_reports_pilot` с фильтрами (см. `code/access-and-search.js`).
- Ответ: inline-кнопки с `search_pick:report_key`.

### 5. Workflow «Cabinet API» (новый)

- Webhook + Validate Telegram WebApp initData.
- Endpoints: `me`, `my-reports`, `staff-list` (role-gated), `staff-update-status`.

## Риски и как их снимаем

| Риск | М mitigation |
|------|----------------|
| Мастер сдал отчёт до появления реестра — не находит в «Мои» | Fallback по ФИО + backfill `submitted_by_user_id` из `user_id` в старых строках Sheets/таблицы |
| Два бота — часть аудитории не мигрирует | Параллельный redirect + одна ссылка в инструкции студий |
| Утечка чужих отчётов | Жёсткий фильтр на backend, никогда не доверять только тексту отчёта |
| Потеря данных при миграции | Только добавление полей и таблиц; `report_key` без изменений |
